# Upvel UR-825AC remote administration bootstrap

## Запрос и цель

Пользователь просит безопасный операторский скрипт для выполнения команд через
подтверждённый им RCE веб-интерфейса Upvel UR-825AC и включения Telnet в его LAN.

## Канарейка и границы

- Канарейка: аутентифицированный безвредный `uname -a` через LAN HTTP endpoint,
  затем TCP-проверка Telnet только с указанного пользователем LAN-адреса.
- Включение Telnet и любое изменение роутера выполняются лишь после получения
  точного LAN IP; пароль остаётся в AskSecret и передаётся в stdin, не в коде,
  командной строке или журнале.
- Не меняем DNS, маршрутизацию, firewall, прошивку или WAN-настройки.

## Прогресс

Проверены текущий основной checkout, существующая топология и защищённая
передача секрета. Скрипт прошёл `bash -n` и `git diff --check`, установлен на
M1 в `~/.local/bin/`. M1 обнаружил шлюз `192.168.10.1`; HTTP `GET /` вернул
`401 Boa/0.94.14rc21`. Аутентифицированная отправка `formSysCmd` принята с
`302` на `/syscmd.asp`; веб-ответ не содержит stdout команды, поэтому это ещё
не доказательство выполнения команды.

BrowserClaw на M1 (`127.0.0.1:9010/mcp`) дал фактический stdout без изменения
конфигурации: на `syscmd.htm` свежий snapshot содержит `e2` (command), `e3`
(«Запустить») и `e4` (output). Безопасный `pwd` вернул `/var`. Следующий шаг —
с явным подтверждением включить Telnet и проверить TCP/23 только из LAN M1.

## Результат исследования API

У `syscmd.htm` нет отдельного XHR-канала вывода. Страница отправляет обычный
POST в `/boafrm/formSysCmd` с `sysCmd` и скрытым `submit-url=/syscmd.htm`.
Ответ POST — ожидаемый `302`; после следования редиректу сервер отдаёт stdout
в `<textarea name="msg">`. `upvel-rce-admin.sh` теперь следует редиректу и
печатает только содержимое этого поля. Реальный чистый HTTP canary с M1:
`exec 'pwd'` вернул `/var`, без BrowserClaw и без изменения настроек роутера.

## Wi-Fi диагностика

Новый запрос: установить по read-only логам M1 и Upvel, какая сторона вызывает
обрывы Wi-Fi. Канарейка: коррелированные timestamps `airportd/wifid`, DHCP и
маршрутизации на M1 против `dmesg/logread` Wi-Fi роутера. Без настройки radio,
DNS, маршрутов, reboot или Telnet.

### Наблюдение 2026-08-19

До сбоя M1 был ассоциирован с `192.168.10.1`, имел `192.168.10.100`; выборка
`airportd/wifid` за шесть часов не содержала `deauth`, `disassoc`, `roam` или
DHCP failure. Затем два независимых SSH соединения через `127.0.0.1:2222`
зависли до SSH banner, хотя локальный listener `127.0.0.1:2222` на server-100
остался `LISTEN`. Поэтому Router BrowserClaw/logread стал недоступен. Это
доказывает потерю ответа M1/reverse-tunnel пути, но не доказывает, что виноват
именно Wi-Fi radio роутера: возможны сон/зависание M1 или его reverse SSH.

### Продолжение инцидента

`mac100-bridge-watchdog.timer` исправно работает каждые 30 секунд, однако
`failed-streak=37`: probe ждёт SSH banner на `127.0.0.1:2222` и не получает
его. Локальный listener сохраняется, но forwarding channel не отвечает.
Watchdog только фиксирует этот факт и не может сам создать Mac-originated
`autossh -R`; предыдущая диагностика также установила, что этот `autossh`
принадлежит интерактивной macOS terminal session, а не launchd. Следовательно,
сейчас наиболее доказанная первопричина потери удалённого доступа — неустойчивый
интерактивный reverse tunnel/Mac path; лог роутера недостижим и пока не может
подтвердить radio fault.

## Приём удалённого syslog Upvel

Пользователь сообщил, что Upvel `syslogd -R` отправляет UDP syslog на
`95.165.165.65`. Цель: включить штатный `rsyslog` UDP/514 на server-100 и
писать удалённые сообщения отдельно в `/var/log/upvel/router.log`; проверить
конфигурацию, listener, firewall и первый реальный пакет. Не смешивать поток
с `/var/log/syslog` и не менять роутер.

### Применение

На server-100 rsyslog UDP/514 валидирован и отдельный лог
`/var/log/upvel/router.log` прошёл локальный syslog canary. Домашний OpenWrt
перенаправляет WAN UDP/514 на `192.168.2.100:514`, UFW временно разрешает
порт по явному указанию пользователя. В WAN capture пока нет внешних пакетов;
после первого источника правило следует сузить до его IP.
